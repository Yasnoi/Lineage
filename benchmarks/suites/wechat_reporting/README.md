# WeChat Reporting 项目任务

这组任务面向接手项目的用户：先理解文档和已有成果，再追查设计依据、识别问题并提出可验证的改进方向。任务覆盖当前只读 Research；完整定义见 [任务索引](task-index.json)，逐轮提示见 [tasks](tasks/)，判定条件见 [Rubric](rubrics/research.json)。当前版本完成离线执行与评分流程验收，尚无新任务的真实模型效果基线。

## 任务与用户目标

| 任务 | 用户目标 | 轮次 | 核对重点 |
| --- | --- | ---: | --- |
| `requirements-coverage` | 理解已完成哪些要求 | 1 | 需求—实现—验证—缺口，区分模板承诺与最终目标、确认记录与措辞变化 |
| `module-purpose` | 理解代码为什么这样设计 | 2 | 模块/调用路径反向对应需求，明确记载与设计推断分开 |
| `defect-reference` | 判断原版局部逻辑是否存在缺陷 | 1 | 签名与表单版本绑定；不虚构问题，不扩大局部结论 |
| `defect-changed` | 定位有明确触发路径的缺陷 | 1 | 构造变体中的旧签名仍有效问题，影响、触发条件和验证办法 |
| `performance-risk` | 判断容量风险和证据不足之处 | 2 | 全量存储读写、复制和线性查找；不将复杂度分析冒充压测 |
| `improvement-plan` | 决定下一步如何推进 | 2 | 基于证据比较至少两种方案，说明代价、边界、实施与验证办法 |
| `handoff-correction` | 修正评估范围并形成交接 | 3 | 模板范围纠正、格式约束跨轮保留，不将纠正话语污染交付物 |
| `read-limit` | 在资料不可读时继续研究 | 2 | 指定测试文件实际超限；回答与已取得材料一致，不编造测试结果 |
| `compaction-continuation` | 摘要后继续模块研究 | 5 | 旧事实、来源、约束经过压缩并被后续请求使用 |

这是八类任务、九个任务实例，共 19 个计划轮次。缺陷原版/构造版用于暴露漏报与误报，当前分别评分，不声称已实现通用配对评分器。前六种研究方向对应需求分析中的 FR-05、FR-06、FR-07，并覆盖 FR-04 的资料冲突与 NFR-05 的执行一致性；辅助场景验证多轮、读取边界及摘要影响。任务不要求唯一的工具调用次序，不因单次回答不足临时补提示。

## 材料与构造边界

[材料清单](materials.json) 固定代码提交 `214b38ef4d813c7ae7ab2defb5406bc4165e8b9b` 的 50 个文本文件，以及资料提交 `917efa1c4355f741486265ecd3d33db3cb0982e3` 的三个 Markdown 文件和两份 PDF 的已核对转写。只从 Git 对象提取白名单，不读取未提交修改、凭据或原仓库其他文件；不切换分支。转写保留原问号和页码，不表示 Agent 支持 PDF 解析。

`code/` 和 `requirements/` 放在每个实例的独立材料根目录，`SOURCE_INDEX.md` 仅给出简短来源说明。详细的来源提交、路径、Git blob、摘要和构造规则保存在根目录外的 `manifest.json`，与执行结果绑定。Rubric、答案边界、Lineage 验收说明和变体编辑规则不进入 Agent 可访问范围；目标项目自身开发与验证文档属于允许材料。

[签名构造变体](variants/signature-staleness.json) 仅在评测副本中停止递增表单 revision 并保留旧签名，原版文档和测试期望保持不变。材料索引标注它是评测构造版本，不提示具体缺陷；其问题不能归因于目标原仓库。`defect-reference` 是原版对照，不预设整个项目没有缺陷。

读取受限任务将单文件上限覆盖为 4 KiB，并要求实际观察到目标测试文件被拒绝。摘要任务添加明确标为评测构造的 6 KiB 无事实背景，保留最近两轮，以既有预算计量按 `max(1, trigger-required+512)` 计算第四轮压力字符，最多 16 KiB。当前离线核对采用 32,768 上下文、4,096 业务输出和任务覆盖的 80% 压缩目标、2,048 摘要输出、4,096 字节摘要上限；生产默认值不变。该任务版本为 2.1，其余任务为 2。

摘要机制需同时满足：前期未提前压缩，旧记录进入摘要输入，摘要及活动版本已保存，后续真实调用参数使用该版本，旧原文移出且后续没有工具重读。近期回答是否泄漏旧事实仍由评审者核对；正确答案本身不能证明机制有效。离线替身已用于检查这些边界，不证明真实模型会遵守确认式回复或保留语义。

## 评分与真实运行准备

评分分为事实与证据、目标覆盖、分析合理性、不确定性与边界、约束与历史、执行一致性。单轮任务不要求历史维度；每题适用必需条件全部满足、无严重错误、必要机制得到确认才能通过。证据不足、未评分、调用失败和真实质量失败各自记录。性能判断只允许基于源码和已有材料提出风险及验证方案，不凭六个模拟用户或存在测试文件认定生产容量已验证。

真实运行前另外核定模型、端点、材料范围、重复次数、预算和评审责任。使用[通用入口](../../README.md)，评测集只传 `wechat-reporting` 这个标识，不使用专属模型或 profile 参数。先做技术试运行，确认材料、轨迹、评分包和必要机制，再冻结条件重复；失败、拒答、异常和覆盖缺口都保留，不挑选最好样本。

人工和 LLM 建议复用同一组条件；当前 LLM 适配仅离线验证，未经真实校准。导入人工确认后的判定才形成已评审结果，修订另存。报告以本次配置的计划实例和各维度适用实例作为分母，质量、可靠性、调用消耗分别报告，无总体发布分数线。旧六题定义和 Rubric 保存在 [history](history/)，历史运行不重新按新题评分。
