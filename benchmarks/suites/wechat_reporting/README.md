# WeChat Reporting 项目任务

这组任务面向接手项目的用户：先理解文档和已有成果，再追查设计依据、识别问题并提出可验证的改进方向。任务覆盖当前只读 Research；完整定义见 [任务索引](task-index.json)，逐轮提示见 [tasks](tasks/)，判定条件见 [Rubric](rubrics/research.json)。执行结果、机制证据和语义判定分别记录；人工评分完成前不将运行产物称为完整效果基线。

## 任务与用户目标

| 任务 | 用户目标 | 轮次 | 核对重点 |
| --- | --- | ---: | --- |
| `requirements-coverage` | 理解已完成哪些要求 | 1 | 需求—实现—验证—缺口，区分模板承诺与最终目标、确认记录与措辞变化 |
| `module-purpose` | 理解代码为什么这样设计 | 2 | 模块/调用路径反向对应需求，明确记载与设计推断分开 |
| `defect-reference` | 判断原版局部逻辑是否存在缺陷 | 1 | 签名与表单版本绑定；不虚构问题，不扩大局部结论 |
| `defect-changed` | 定位有明确触发路径的缺陷 | 1 | 构造变体中的旧签名仍有效问题，影响、触发条件和验证办法 |
| `performance-risk` | 判断容量风险和证据不足之处 | 2 | 全量存储读写、复制和线性查找；不将复杂度分析冒充压测 |
| `improvement-plan` | 决定下一步如何推进 | 2 | 基于证据比较至少两种方案，说明代价、边界、实施与验证办法 |
| `handoff-correction` | 修正评估范围并形成交接 | 3 | 模板范围纠正、格式约束跨轮保留，不将纠正话语污染交付物 |
| `read-limit` | 在资料不可读时继续研究 | 2 | 指定测试文件实际超限；回答与已取得材料一致，不编造测试结果 |
| `compaction-continuation` | 摘要后继续模块研究 | 6 | 旧事实、来源、约束经过 H 压缩并被后续请求使用 |
| `history-recall` | 单 Run 压缩后回查遗漏细节 | 1 | 16 份小结果经过 R 压缩，按稳定引用搜索和读取原始记录 |

当前定义包含十个任务实例，共 21 个计划轮次。缺陷原版/构造版用于暴露漏报与误报，当前分别评分，不声称已实现通用配对评分器。前六种研究方向对应需求分析中的 FR-05、FR-06、FR-07，并覆盖 FR-04 的资料冲突与 NFR-05 的执行一致性；辅助场景验证多轮、读取边界及摘要影响。任务不要求唯一的工具调用次序，不因单次回答不足临时补提示。

## 材料与构造边界

[材料清单](materials.json) 固定代码提交 `214b38ef4d813c7ae7ab2defb5406bc4165e8b9b` 的 50 个文本文件，以及资料提交 `917efa1c4355f741486265ecd3d33db3cb0982e3` 的三个 Markdown 文件和两份 PDF 的已核对转写。只从 Git 对象提取白名单，不读取未提交修改、凭据或原仓库其他文件；不切换分支。转写保留原问号和页码，不表示 Agent 支持 PDF 解析。

`code/` 和 `requirements/` 放在每个实例的独立材料根目录，`SOURCE_INDEX.md` 仅给出简短来源说明。详细的来源提交、路径、Git blob、摘要和构造规则保存在根目录外的 `manifest.json`，与执行结果绑定。Rubric、答案边界、Lineage 验收说明和变体编辑规则不进入 Agent 可访问范围；目标项目自身开发与验证文档属于允许材料。

[签名构造变体](variants/signature-staleness.json) 仅在评测副本中停止递增表单 revision 并保留旧签名，原版文档和测试期望保持不变。材料索引标注它是评测构造版本，不提示具体缺陷；其问题不能归因于目标原仓库。`defect-reference` 是原版对照，不预设整个项目没有缺陷。

读取受限任务将单文件上限覆盖为 4 KiB，并要求实际观察到目标测试文件被拒绝。跨轮摘要任务 v5 使用 65536 的窗口和明确标为评测构造的 6 KiB 无事实背景。第五轮复用运行入口的上下文继承函数，按完整业务候选的预算结果，在 0–32 KiB 范围内二分选择使请求刚好超限的 ASCII 压力长度；达到上限仍放得下时记录机制缺口。保护窗口只覆盖当前 Run 最近三个完整业务组，全部已结束旧轮次可进入 H，因此第五轮应选择前四轮而不产生 R。第六轮检查旧事实、来源和约束是否实际经过 H 保存并用于回答。[旧 v4 定义](history/compaction-continuation-v4.json)、[旧 v3 定义](history/compaction-continuation-v3.json)、[旧 v2.3 定义](history/compaction-continuation-v2.3.json) 与[旧 v2.2 定义](history/compaction-continuation-v2.2.json) 保留供历史结果回访。

`history-recall` v3 使用[版本化静态资料链](fixtures/history-chain-v1/)，每份 2301–3301 UTF-8 字节，完整 Observation envelope 在 4 KiB 内，避免用小结果 Artifact 代替原始记录回读。资料不描述目标项目；第 16 份才指出需要回查的记录键。模型应先按顺序读取各份资料，再通过 `history_search` 和 `history_read` 回查已被 R 覆盖的原始记录，不能重新打开旧文件。任务要求保留数字、否定条件和修正，并提供原文证据。[旧 v2 定义](history/history-recall-v2.json) 保留原输出上限供历史结果回访。

两项机制例使用小窗口，使固定任务能覆盖压缩路径。H/R 摘要请求均使用 16384 的输出 token 上限和预算预留，不分配生成软目标，不要求额外百分比恢复余量。完整业务候选预算允许、净回收为正并确认保存后提交。每个业务请求最多两次完整尝试，每次 H/R 各至多一次调用；只有完整有效候选仍超限才允许第二次，候选预算允许但净回收非正时直接停止。实际触发、提交及原文回读都以真实请求和保存事实核验，不能由配置数字直接宣布通过。

跨轮机制同时检查原始记录不变、旧正文移出、后续真实调用参数使用已保存摘要和禁止重读。单 Run 机制检查完整资料链、inline 返回、R 覆盖、目标原文移出、历史检索与读取的引用绑定及准确原文。正确答案不单独证明机制有效；摘要遗漏、数字/否定/修正是否保持、回答是否正确使用证据仍需来源复核。若目标细节仍在真实摘要中，报告回读已观察但遗漏恢复条件未覆盖，不修改摘要制造通过。

每轮额外保存本地 `turn-XX-compact-evidence.json`，包括所有 Compact 尝试事件、实际摘要来源、摘要输出和历史召回；这些是本地评审资料，不改变生产追踪过滤。指标单列历史工具固定 schema 占用、H/R 调用、压缩前后占用、净回收、候选剩余预算、召回次数/字节和可获得的记录存储量。逻辑字节与保存点序列化字节不代表进程实际内存。

## 配置继承与任务选择

使用[通用入口](../../README.md)及运行配置 v2：`agent_source: "project_env"` 从当前生产配置加载模型和连接字段，优先级为任务覆盖 > `model_overrides` > 进程环境 > 项目根 `.env` > 默认值。没有环境或显式覆盖时，当前生产默认值为每轮 30 次业务调用、请求超时 300 秒、窗口 250000、输出上限 16384、预留 8192；执行结果记录实际解析后的安全字段，不假定本机始终等于默认值。运行配置仅支持 v2，旧版本明确拒绝。

| 原预算或配置 | 当前处理 |
| --- | --- |
| 普通研究任务预算 | 按生产配置和显式 `model_overrides` 解析，不重复维护一套研究默认值 |
| 单文件读取受限 4 KiB | 仅 `read-limit` 保留，其他读取限制按生产配置继承 |
| 摘要小窗口与压力 | 两项 Compact 机制例固定窗口 65536、当前 Run 最近三组；H/R API 输出上限均为 16384；跨轮例第五轮压力最多 32 KiB |
| 已移除的 Compact 配置 | `context_trigger_percent`、`context_target_percent`、`summary_max_output_tokens`、`summary_max_bytes`、`context_keep_recent_turns`、`summary_target_percent`、`context_recovery_margin_percent` 均须删除，不能映射为新配置；组保护用 `context_keep_recent_groups`，分路输出上限用 `summary_history_max_output_tokens` 和 `summary_run_max_output_tokens` |
| 批次与实例上限 | 独立于生产模型额度显式填写，不随生产默认值扩大；硬上限 400 次请求、7200 秒累计、每实例 1200 秒 |

在项目根目录执行 `uv run --locked python -m benchmarks list wechat-reporting`，可查看可选任务 ID、标题和轮次。必填的 `units` 决定本次任务范围和顺序；`repeats` 决定重复次数。批次请求、累计时间及样本时间在运行配置中指定，所有选定样本共用批次记账，不自动重试。任务数和轮次以本次计划为准，不要求执行全部任务。

启用 `gate_first_sample` 后，首例必须可信完成，并可回访本地日志、适用检查点、回答文件及其摘要，才继续调度；该技术检查不等待语义评分、摘要机制或远端追踪通过。外部上传默认关闭；需要上传时设置 `tracing.enabled: true`，并在 `tracing.unit_ids` 选择本次任务的子集。每个启用追踪的实例最多三轮远端查询、合计 30 秒，纳入配置的累计时间预算。

追踪遵循生产过滤。报告区分未启用、本地提交完成/不完整和远端已核验等事实；未取得远端证据时不声称上传已确认。实际完成、失败、未执行及消耗以独立运行报告为准；没有可核验账单时费用为未知。一次执行只能提供该次观察，不支持稳定性结论。

## 评分与真实运行准备

评分分为事实与证据、目标覆盖、分析合理性、不确定性与边界、约束与历史、执行一致性。单轮任务不要求历史维度；每题适用必需条件全部满足、无严重错误、必要机制得到确认才能通过。证据不足、未评分、调用失败和真实质量失败各自记录。性能判断只允许基于源码和已有材料提出风险及验证方案，不凭六个模拟用户或存在测试文件认定生产容量已验证。

评测集只传 `wechat-reporting` 这个标识，不使用专属模型或 profile 参数。每次运行冻结任务、材料、解析配置与评分版本，失败、拒答、异常和覆盖缺口都保留，不挑选最好样本。改变模型、材料或调用预算后应另存运行，不能用新条件下的成功覆盖旧结果。

Rubric 的 `judge_scope` 指定模型建议范围：回答、源码、不确定性及可见对话约束允许生成建议；实际查阅、执行一致性、读取失败和摘要机制由人工核对。严重错误仅 `unsupported-certainty` 允许模型建议，其他严重错误由人工核对。模型不能据可见回答证明历史或摘要来源，未经人工确认的建议保持待评审；当前模型评审适配仅离线验证，未经真实校准。Judge 凭据只读取进程环境，设置步骤见[评审说明](../../README.md)。

导入人工确认后的判定才形成已评审结果，修订另存。报告以本次配置的计划实例和各维度适用实例作为分母，质量、可靠性、调用消耗分别报告，无总体发布分数线。旧定义和 Rubric 保存在 [history](history/)，历史运行不重新按新题评分，历史产物直接查看原有文件。
